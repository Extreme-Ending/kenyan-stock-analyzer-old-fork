KENYAN STOCK ANALYZER — FEATURE ROADMAP
================================================================
Broader feature roadmap beyond data-analysis/accuracy work.
See IMPROVEMENTS.txt for data-quality items (scoring accuracy,
backtesting, price/fundamentals validation, horizon labels).
See CLAUDE.md for engineering standards these should follow.

Each item: current state -> problem/opportunity -> proposed approach.


================================================================
0. TARGET DEPLOYMENT ARCHITECTURE (constraint for everything below)
================================================================

Decided direction (revised 2026-09-04, see STATUS below): dashboard
hosting is GitHub Pages, not S3 -- an AWS/S3 attempt was built, tested,
and deliberately torn down the same day (see 0a's STATUS for why and
what was learned). Lambda (compute) and SNS (notification fan-out)
remain open ideas, not decided -- GitHub Actions has proven sufficient
for both the notification pipeline (daily-summary.yml, live) and the
full dashboard build (~4 min locally, well inside Actions' free-tier
limits), so there's no evidence yet that either is actually needed.
Terraform is parked; nothing here currently depends on it.

0a. Dashboard hosting
--------------------------------------------------------------
Confirmed in code: report_generator.py embeds every chart as a
base64 PNG directly inside the HTML (`data:image/png;base64,...`,
see _fig_to_base64 and the chart-embedding call sites). Every
generated report is a single self-contained HTML file — no
separate image assets to keep in sync. That's what makes any
static host (S3, GitHub Pages, ...) trivial: no CDN-asset-pipeline
complexity needed, just sync/publish the reports/ directory as-is.

STATUS (2026-09-04): Live on GitHub Pages --
https://extreme-ending.github.io/kenyan-stock-analyzer/ . New
.github/workflows/deploy-pages.yml rebuilds the full dashboard
(`python main.py --force-refresh --no-email`, lean scope -- no
--detailed/--export-excel, keeps runs fast and report_format defaults
to html so no WeasyPrint system libs needed) and publishes it via
GitHub's own actions/upload-pages-artifact + actions/deploy-pages, on
the same three daily checkpoints as daily-summary.yml (open/mid/close,
so the live dashboard refreshes right when notifications go out) plus
every push to main. No AWS, no IAM/OIDC to maintain -- GitHub manages
the Pages deployment's auth internally. Verified live (HTTP 200,
correct page title) after the first real push-triggered deploy.

An S3 approach was tried first and worked technically, but was fully
torn down the same session at the project owner's explicit request
("I want all this to be private") once it became clear that even
non-secret AWS identifiers (the account ID, via an IAM role ARN printed
in a public Actions log -- GitHub only auto-redacts `secrets.*`
values, never `vars.*`, and this repo's Actions logs are public since
the repo itself is) were leaking into public GitHub Actions logs on a
public fork. Confirmed nothing was left exposed afterward: the S3
bucket, its public-read policy, the GitHub OIDC identity provider, the
IAM role, and the GitHub repo variables were all deleted; the leaking
Actions run itself was deleted (not just its workflow file); a full
sweep of git history, remaining secrets/variables, and all workflow
runs turned up zero remaining AWS-identifying traces. GitHub Pages was
chosen over rebuilding the S3 route because it fully sidesteps the
problem class (no AWS account involved at all, so nothing AWS-specific
can leak) and matches the "simple and cheap" preference better --
zero IAM/OIDC surface to get wrong, free, and it's what's live today.
Engineering notes kept in case S3 (or any AWS-OIDC integration) is
ever revisited for something else:
  - GitHub's OIDC token `sub` claim was NOT the classic
    `repo:OWNER/REPO:ref:refs/heads/BRANCH` format -- it came through as
    `repo:OWNER@<org_id>/REPO@<repo_id>:ref:refs/heads/BRANCH` (an
    "immutable ID" format, confirmed via CloudTrail after an
    AssumeRoleWithWebIdentity AccessDenied). An IAM role trust policy
    needs a StringLike condition covering both
    `repo:Extreme-Ending/kenyan-stock-analyzer:ref:refs/heads/main` and
    `repo:Extreme-Ending@*/kenyan-stock-analyzer@*:ref:refs/heads/main`
    (or the exact immutable IDs) to actually match.
  - Never put an AWS identifier (ARN, account ID, bucket name) in a
    workflow `vars.*` if the repo is public and the value should stay
    private -- only `secrets.*` gets redacted in Actions logs, and
    those logs are public on a public repo regardless of collaborator
    permissions.
Known limitation, still applies to the live GitHub Pages setup too:
data/history/daily_snapshots.csv (IMPROVEMENTS.txt item 2's backtest
input) doesn't persist between GitHub Actions runs (ephemeral runner,
data/ is gitignored) -- the deployed Track Record page will always
show "insufficient_history" until history gets a persistent store
(ties into section 2's CSV->SQLite item; SQLite alone doesn't fix this
unless the DB file itself is synced somewhere across runs too).
0b. Lambda — compute constraints to design around
--------------------------------------------------------------
Two real constraints, both worth checking before committing code
to run there:
  - PACKAGE SIZE: requirements.txt pulls in matplotlib, scipy,
    pandas, numpy, seaborn, weasyprint — heavy. Zip-based Lambda
    has a 250MB unzipped limit; this stack is likely to blow past
    that. Use a container-image Lambda (up to 10GB, and the venv
    we already built here is a good starting point for the image)
    rather than fighting zip/layer size limits.
  - EXECUTION TIME: Lambda's hard cap is 15 minutes. Our local
    full run (--detailed --export-excel, 55 stocks, individual
    reports + Excel) took ~7.5 minutes end-to-end (16:31:41 to
    16:39:14 in our test run). That fits, but with less margin
    than we'd like, especially with S3-network variance from
    inside Lambda instead of local disk. The LEAN path
    (send_summary.py — watchlist + summary only, no per-stock
    HTML) is much faster and safely fits.
  Recommendation: run send_summary.py's lean pipeline on Lambda
  first (matches section 1's push-notification use case exactly).
  For the full detailed dashboard regen, benchmark actual Lambda
  runtime before assuming it fits — if it's tight, ECS
  Fargate (no 15-minute ceiling) is the fallback for that specific
  job while Lambda still handles the fast daily-summary path.

0c. SNS — notifications
--------------------------------------------------------------
SNS is a good fit as a FAN-OUT HUB, not a drop-in replacement for
today's SMTP-based email_notifier.py:
  - SNS email delivery is plain text (or JSON), not MIME with a
    PDF attachment — it can't do what email_notifier.py currently
    does (send the actual PDF as an attachment).
  - Best fit: Lambda uploads the PDF summary to S3 (0a), then
    publishes ONE SNS message (short text: headline alerts +
    a link to the S3-hosted PDF); SNS fans that single publish out
    to every subscriber — an email subscription, optionally an SMS
    subscription, and an HTTPS subscription endpoint that forwards
    into the Telegram/WhatsApp adapters from section 1a. This
    reuses the "one payload, many channel adapters" design already
    planned in 1a — SNS becomes the fan-out mechanism instead of
    each channel being called directly from send_summary.py.
  - Keep SMTP as a fallback/direct option only if we specifically
    want the PDF as a real email attachment rather than a link —
    otherwise SNS is simpler and matches the S3+Lambda shape.


================================================================
1. NOTIFICATIONS — Telegram + WhatsApp
================================================================

Current: one channel — email, via src/email_notifier.py, triggered
by .github/workflows/daily-summary.yml (send_summary.py) on a
GitHub Actions schedule.

Goal: add Telegram and WhatsApp as additional (not replacement)
channels for the same daily summary, and design it so more
channels can be added later without rewriting the send path.

1a. Shared design — build once, reuse for every channel
--------------------------------------------------------------
Extract a generic notifier interface (mirrors email_notifier.py's
shape): send_summary.py already builds ONE summary payload
(market pulse, watchlist, gainers/losers, alerts, upcoming
ex-dividends) before handing it to the emailer. Each channel
(email/Telegram/WhatsApp/future) should be a thin adapter that
takes that same payload and formats+sends it its own way —
never duplicate the "what to say" logic per channel.

1b. Telegram (do this first — cheapest to stand up)
--------------------------------------------------------------
- Free, official Bot API, no business verification needed.
- Setup: create a bot via @BotFather, get a bot token, get the
  target chat_id(s) (personal chat or a channel/group).
- Two shapes, pick one to start:
  (i)  PUSH ONLY (recommended first step) — reuse the existing
       scheduled GitHub Actions workflow; after building the
       summary, POST it to the Telegram Bot API
       (sendMessage / sendDocument for the PDF) using `requests`
       — no persistent process needed, fits the current
       "throwaway GitHub Actions runner" architecture exactly.
  (ii) INTERACTIVE BOT (/price SCOM, /watchlist, on-demand) —
       a webhook shape now fits the decided architecture (0):
       API Gateway + Lambda receiving Telegram's webhook, reading
       the latest scores from S3 (or the read API in section 7)
       instead of re-running the whole pipeline. Long-polling does
       NOT fit Lambda (no long-running process) — webhook is the
       right shape here, not polling. Still sequence this after
       1b-i (push) is working and after section 7's read API
       exists, since the bot needs fast on-demand data, not a
       full pipeline re-run per query.
- Secrets: TELEGRAM_BOT_TOKEN, TELEGRAM_CHAT_ID as GitHub Actions
  secrets, same pattern as EMAIL_USER/EMAIL_PASSWORD.

STATUS (2026-09-03): 1b-i's local half is done and tested.

TELEGRAM_CHAT_ID supports multiple comma-separated chat IDs

1b-ii (interactive bot / webhook) remains correctly sequenced after this

Two follow-on fixes landed in the same pass, both live-verified against

  - The summary PDF's Watchlist table was missing two fields that

STATUS (2026-09-04, 1b-ii): Built, differently from this section's
original plan -- API Gateway + Lambda was the assumption when this was
written, but AWS was ruled out entirely for this project (see 0a's
STATUS). Went with short-interval polling instead of a webhook: GitHub
Actions can't run an always-on server to receive one, so a new
.github/workflows/telegram-poller.yml polls Telegram's getUpdates every
5 minutes (GitHub's minimum cron granularity) via telegram_poller.py.
No local state needed to track already-seen messages -- passing
offset=<last update_id>+1 back to Telegram marks them consumed
server-side for good, regardless of which process polls next.
Also skipped waiting on section 7's read API: rather than serving
pre-computed scores from a JSON blob, an on-demand request just re-runs
send_summary.py's lean pipeline directly (new build_summary() function,
extracted out of send_summary.py's main() so both call sites share it) --
simpler, no extra data plumbing, at the cost of a ~1-2 min reply instead
of instant. Two behaviors, by sender:
  - Owner's configured TELEGRAM_CHAT_ID sending exactly "/refresh" ->
    triggers a full data refresh AND a dashboard rebuild+redeploy (a
    second workflow job, gated on a `refresh_requested` output from the
    polling job) -- sent back to the owner only, never broadcast, so
    testing doesn't spam other subscribers.
  - Anyone else's first message -> added to a new persisted subscriber
    list (src/telegram_subscribers.py,
    data/history/telegram_subscribers.json, committed back to the repo
    by the poller workflow -- ephemeral runners need this to survive
    across runs) and immediately sent the current summary + PDF as a
    welcome. send_summary.py's mid/close Telegram checkpoints now
    broadcast to this list too (unioned with the owner's fixed config),
    not just the originally-configured chat ID -- this was an explicit
    scope change from the project owner mid-build ("anyone who adds the
    bot... should receive... the 3 crons response").
Every Telegram message (scheduled or on-demand) now also links the live
dashboard (telegram_notifier.DASHBOARD_URL, appended in
generate_summary_text()), tying back into 0a's GitHub Pages deployment.
14 new tests (subscriber list persistence incl. corrupt-file fail-safe;
get_updates/send_message_to/send_document_to incl. failure modes; the
owner-vs-stranger /refresh routing logic specifically, since misrouting
that is the one security-relevant bug this design could have). Not yet
verified live -- next step is push + a real /refresh from the owner's
Telegram to observe end-to-end.

1c. WhatsApp (real constraints — decide before building)
--------------------------------------------------------------
Unlike Telegram, WhatsApp has no free/instant personal-bot route.
Two real options, both need a decision up front:
  (i)  Meta WhatsApp Cloud API (official, free tier exists) —
       requires a Meta Business account, phone number
       verification, and app review for anything beyond a small
       set of pre-approved template messages to first-time
       recipients. Setup friction is real but it's free at low
       volume and is the "proper" long-term route.
  (ii) Twilio WhatsApp API (third-party) — faster to set up
       (sandbox available immediately for testing), but paid
       per-message beyond the sandbox, and production requires
       WhatsApp Business approval through Twilio too.
  Recommendation: prototype with Twilio's sandbox (fast, no
  business verification needed for testing), decide on Cloud API
  vs Twilio for production once the notification is proven useful.
- Push-only fits the same GitHub Actions job as Telegram — send
  the summary as a WhatsApp template message after building it.
- Secrets: WHATSAPP_* tokens/IDs as GitHub Actions secrets.

1d. Per-user delivery preferences
--------------------------------------------------------------
Today .env has ONE shared watchlist and ONE recipient list.
Once there's more than one channel, worth deciding: does everyone
get every channel, or can a user pick (e.g. Telegram only)? Keep
this simple (a config list of {channel, destination}) rather than
building real user accounts unless there's demand for that.

2. RELIABILITY / OPERATIONS
================================================================

- Retry/backoff + circuit-breaking tuned per data source. Some
  sources (CBK, T-bills, bonds pages) came back "unavailable" in
  our test run — worth checking whether those scrapers are
  actually broken (site changed) vs. just flaky, since a broken
  scraper and a flaky one need different fixes.
- CI: run test.py on every push/PR via GitHub Actions, separate
  from the existing daily-summary.yml scheduled job.
  STATUS (2026-09-04): Done. New .github/workflows/tests.yml runs
  test.py on every push to main and every PR, matrix over Python
  3.12 and 3.13 (pip-cached). Building this surfaced a real, unrelated
  bug: README.md/CLAUDE.md both claimed a "Python 3.10+" baseline, but
  requirements.txt's actual pins forced 3.12+ (numpy>=2.5.0 requires
  3.12; tvkit>=0.11.2 alone would have forced 3.11+) -- caught because
  the 3.10 and then 3.11 matrix legs failed at dependency install on
  real GitHub-hosted runners, not a local guess. Corrected the stated
  baseline in both docs to 3.12+ in the same change. Verified green on
  both matrix legs on the actual runner.
- Dockerize the pipeline — run.sh still assumes a macOS desktop
  (Homebrew's DYLD_LIBRARY_PATH); a Dockerfile removes "works on
  my machine" issues and is also a prerequisite for a clean
  ECS/Fargate deployment if we go that route later.
  STATUS (2026-09-03): The two acute bugs in run.sh are fixed
  (not the full Dockerization, still tracked above): SSL_CERT_FILE
  was hardcoded to a python3.14 site-packages path, breaking every
  HTTPS fetch with "[Errno 2] No such file or directory" on any
  other Python version (hit on a real Python 3.12 venv) — now
  derived from `certifi.where()` at runtime. `open` at the end
  (macOS-only) now falls back to `xdg-open` or just prints the
  path. DYLD_LIBRARY_PATH is now guarded to macOS only.
- Move data/history/daily_snapshots.csv to SQLite (or Postgres if
  we're already provisioning a database for something else) —
  CSV read-modify-write gets slower and is fragile under
  concurrent/scheduled runs as history grows.

5. OBSERVABILITY / DATA-SOURCE HEALTH  (new — not previously listed)
================================================================

Current: when a scrape source fails, it logs a WARNING and the
pipeline degrades gracefully (per CLAUDE.md's fail-safe rule) —
but nobody is watching those warnings. In our test run, CBK,
T-bills, and bonds pages were all "unavailable" and that's easy
to miss for weeks since the dashboard still renders fine without
them.

Proposed: persist a per-run health record (which sources
succeeded/failed, alongside history_tracker.py's existing daily
snapshot) and alert through the new notification channels (once
section 1 exists) when a source has been down for N consecutive
runs. Turns a silent degrade into a visible, actionable signal.

6. SECURITY & SCRAPING RESILIENCE  (new — not previously listed)
================================================================

- Dependency vulnerability scanning — enable GitHub Dependabot
  alerts (free for public repos) or add `pip-audit` to CI.
- The tool scrapes several third-party sites (TradingView,
  afx.kwayisi.org, mystocks.co.ke, NSE PDF, oil/FX/news sources).
  Worth documenting scraping etiquette explicitly (honest
  User-Agent, reasonable request spacing, respecting robots.txt
  where present) — getting IP-banned or ToS-flagged on any of
  these would break real functionality, not just a nice-to-have.
- Secrets hygiene is already decent (.env gitignored, GitHub
  Actions secrets used correctly) — CLAUDE.md formalizes this
  going forward, nothing new to build here.


================================================================
7. LIGHTWEIGHT READ API  (new — not previously listed, optional)
================================================================

Current: output is only static HTML/PDF/Excel files generated
per run; nothing can query "what's SCOM's score right now"
programmatically.

Opportunity: a small read-only API — API Gateway + Lambda (fits
the decided architecture in section 0 directly, no new hosting
type needed) reading the latest scores/prices from a small S3
JSON object that main.py writes alongside the HTML each run
(cheapest: no database needed, just one more S3 object per run)
would:
  - unlock the INTERACTIVE Telegram bot mode (1b-ii) without
    re-running the whole pipeline per query
  - make future integrations (mobile view, a simple web app)
    much easier than parsing generated HTML
Not urgent — only build this once an interactive bot or another
consumer actually needs it.


PRIORITY SUGGESTION
================================================================
(Updated 2026-09-04 -- several of these are done; kept the original
numbering's intent but marked status inline so this list stays a
useful guide instead of going stale silently.)

1. Telegram push notification (1b-i) — DONE, live-verified.
2. Dashboard hosting (0a) — DONE, live on GitHub Pages (not S3 --
   see 0a's STATUS for why). Refreshes 3x/day + on every push.
3. CI running test.py on push/PR (2) — DONE, also caught and fixed
   a real stale-docs bug (claimed Python 3.10+, actually 3.12+).
4. Dashboard filtering (3) — DONE (sector/signal/horizon filters).
5. Observability on data-source health (5) — not started. Cheap,
   prevents silent breakage of things already built (CBK/T-bills/
   bonds outages currently go unnoticed).
6. Security scanning (6) — not started. Cheap, enable and forget
   (Dependabot / pip-audit).
7. CSV->SQLite for history (2) — not started. Also unblocks the
   Track Record page actually accumulating data on GitHub Pages/
   Actions (see 0a's known limitation -- ephemeral runners lose
   data/ every run regardless of CSV vs SQLite unless the DB file
   itself is persisted somewhere across runs).
8. Expanded test coverage (4) — ongoing; dividend_calendar.py and
   earnings_calendar.py still have zero coverage despite CLAUDE.md
   flagging them by name.
9. Dockerize the pipeline (2) — only the two acute run.sh bugs are
   fixed, not full containerization. Lower priority now that both
   the notification job and the dashboard build run fine on plain
   GitHub Actions runners -- no longer a prerequisite for anything
   currently planned (Lambda/ECS are undecided, see section 0).
10. WhatsApp push notification (1c) — not started, real setup
    friction (Meta Business verification or Twilio), do only once
    there's demand for a channel beyond Telegram/email.
11. Interactive bot (1b-ii) — DONE, via polling not a webhook (no
    AWS). Pending live verification (push + a real /refresh to
    observe). Section 7's read API remains not started/optional --
    the bot re-runs the lean pipeline on demand instead of needing it.
12. Lambda/SNS for the notification pipeline (0b/0c) — not decided.
    No evidence yet that GitHub Actions is insufficient for this
    project's scale; revisit only if that changes.
