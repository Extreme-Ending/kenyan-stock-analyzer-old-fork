KENYAN STOCK ANALYZER — DATA ANALYSIS & ACCURACY IMPROVEMENTS
================================================================
Tracking file for planned work to make the tool as accurate as possible.
Scope: data analysis & data quality only (deployment/CI/infra tracked separately).
Each item: current state -> problem -> proposed fix.


1. SCORING DOESN'T USE SECTOR-RELATIVE VALUATION (highest priority)
--------------------------------------------------------------
Where: src/scoring.py (_score_value), src/market_context.py (valuation_vs_sector)

Current: market_context.py already computes per-sector median P/E, P/B,
dividend yield, and ROE, and exposes valuation_vs_sector() to compare a
stock against its sector peers. This is shown on the fundamentals page.

Problem: scoring.py's _score_value() ignores it and scores every stock on
the same fixed absolute curve (e.g. "P/E 8 -> 100, P/E 33 -> 0"). A bank
(naturally low P/E) and a manufacturer (naturally higher P/E) are scored
on an identical scale, which is not a fair comparison.

Fix: pass sector_medians into score_stock() and score P/E, P/B, dividend
yield, and ROE relative to the stock's own sector median instead of (or
blended with) the fixed absolute breakpoints.

STATUS (2026-09-03): Done. score_stock()/_score_value()/_score_quality()/
_score_dividend() now take an optional sector_medians param (from
market_context.compute_sector_medians()) and blend each metric 50/50 with
a sector-relative score (50=in line with sector median, scaled linearly
above/below); reasons record the verdict (e.g. "P/E 4.6 (sector: cheaper
than sector)") per the transparency pattern. Sectors below MIN_SECTOR_PEERS
(3) fall back to the absolute curve alone -- fail-safe against noisy
1-2 stock buckets. Wired into both main.py and send_summary.py. Verified
against real fundamentals data: Finance (22 stocks), Process Industries
(10), and other well-populated sectors get real sector-relative scores;
thin single-stock TradingView industry buckets (e.g. "Communications")
correctly fall back to absolute-only. Covered by test.py's TestScoring
(7 tests: absolute-only baseline, reward/penalize vs sector, thin-sector
fallback, missing-median fail-safe, ROE/dividend-yield blending, alerts).


2. NO BACKTESTING / ACCURACY FEEDBACK LOOP
--------------------------------------------------------------
Where: src/history_tracker.py, data/history/daily_snapshots.csv

Current: every run appends price, signal, and score per stock to a CSV.
Nothing ever reads it back.

Problem: the tool has zero evidence that its own "bullish"/"strong buy"
calls actually perform. No way to know if the scoring model works.

Fix: build a backtest module that joins daily_snapshots.csv against
itself N trading days forward (e.g. 5/20/60 days) and reports: hit rate
per signal type, average forward return per score bucket (0-20, 20-40,
... 80-100), and per-factor (value/quality/momentum/dividend/liquidity)
correlation with forward returns. Surface a summary on the dashboard
("Track record" page) once enough history has accumulated.

STATUS (2026-09-03): Done. New src/backtest.py: run_backtest() joins
HistoryTracker.load_history() against itself per symbol N recorded runs
forward (not calendar days -- a symbol only has a row for a day the
pipeline ran) via groupby('symbol')['price'].shift(-horizon), for
horizons (5, 20, 60). Reports hit_rate_by_signal (bullish=positive
return, bearish=negative, neutral=within +/-2%), avg_return_by_score_
bucket (five 0-100 buckets), and factor_correlation (Pearson r per
sub-score vs forward return, skipped below 3 paired points). A horizon
without enough recorded days reports 'insufficient_history' explicitly
rather than a misleading stat from 1-2 points -- fail-safe per CLAUDE.md,
and the real, current, expected state today (this repo has 1 day of
history recorded so far; all three horizons correctly report that).
Required extending history_tracker.py's schema to also record the 5
sub-scores (score_value/quality/momentum/dividend/liquidity), not just
the overall blend -- old rows without those columns are handled
automatically (NaN, skipped) since a column-missing history DataFrame is
also exactly the "not upgraded yet" fail-safe case, tested directly.
New "🎯 Track Record" dashboard page (report_generator.py's
_build_track_record_body/_track_record_horizon_section) wired into
main.py after history recording, color-coded (green/amber/red) hit
rates, bucket returns, and correlations, reusing the existing fgood/
fmid/fbad verdict classes. 14 new tests (forward-return math verified
against a hand-computed expected value, perfect-directional-data hit
rates, score-bucket split, positive correlation on a constructed
score-proportional dataset, missing-column graceful skip, empty/None/
too-few-days fail-safe paths, history_tracker round-trip). Verified
against a real run (correctly shows "insufficient_history" for all
three horizons at 1 day recorded) and against synthetic 'ok'-status
data rendered through the real _build_track_record_body to confirm the
populated tables display correctly (screenshotted, not just unit-tested).


3. SCORING WEIGHTS AND COEFFICIENTS ARE HAND-PICKED, NOT CALIBRATED
--------------------------------------------------------------
Where: src/scoring.py (DEFAULT_WEIGHTS, all _score_* linear coefficients)

Current: weights (value 0.25, quality 0.25, momentum 0.20, dividend 0.15,
liquidity 0.15) and every sub-score curve are guessed constants.

Problem: no statistical basis for these numbers.

Fix: depends on #2 (backtesting). Once forward-return data exists per
factor, refit weights/coefficients against actual NSE performance instead
of intuition. Re-run periodically (e.g. quarterly) as more history accrues.


4. MOMENTUM SUB-SCORE MAY DOUBLE-COUNT THE TECHNICAL SIGNAL
--------------------------------------------------------------
Where: src/scoring.py (_score_momentum), src/analysis_engine.py

Current: _score_momentum() blends the `overall` bullish/bearish/neutral
signal AND RSI into the momentum score, but `overall` is itself already
derived partly from RSI/MACD in analysis_engine.py.

Problem: correlated inputs risk inflating momentum score's effective
weight beyond what DEFAULT_WEIGHTS intends.

Fix: audit analysis_engine.py's `overall` signal derivation; either
decorrelate the inputs (e.g. drop raw RSI from momentum score since it's
already baked into `overall`) or explicitly account for the correlation
when calibrating weights (#3).


5. PRICE VALIDATION IS SINGLE-SOURCE WITH A STATIC DISAGREEMENT THRESHOLD
--------------------------------------------------------------
Where: src/price_validation.py

Current: only one independent reference (afx.kwayisi.org). Fixed 1%
disagreement threshold for every stock.

Problem: if afx.kwayisi.org is unreachable, validation silently degrades
to "unverified" for the entire run — no fallback reference. A flat 1%
threshold produces more false "mismatch" flags on thinly-traded/illiquid
stocks (naturally wider spreads) than on liquid ones.

Fix: add a second independent reference source as fallback (e.g. NSE's
own daily PDF price list, already used elsewhere in data_acquisition.py
as a fallback — reuse it here). Scale disagree_threshold_pct by a
liquidity proxy (e.g. value_traded or average daily volume) instead of
using one flat threshold for all 57 stocks.

STATUS (2026-09-03): Done. Fallback source: DataAcquisition gained
get_pdf_price_board() (reuses the same per-day _pdf_cache as
get_all_stocks_from_pdf()/the 'nse_pdf' data source -- costs nothing
extra if that ran anyway, and only downloads+OCRs once even if both are
called). price_validation.py's fetch_reference_prices() tries
afx.kwayisi.org first, falls back to the PDF board only if afx fails,
and tracks which source actually answered (self._reference_source,
surfaced in validate()'s reference_source/note fields) -- degrades to
"unverified" only if BOTH fail, not just afx. Liquidity-scaled
threshold: new _avg_value_traded() (KES, last 20 traded bars) and
_liquidity_multiplier() scale disagree_threshold_pct by tier (>=10M/day
-> 1x unscaled, >=1M -> 2x, >=100K -> 3x, thinner/unknown -> 5x, fail-
safe toward the most tolerant tier when volume data is missing) --
validate() now returns threshold_pct and liquidity_multiplier alongside
the existing fields for transparency. 14 new tests for a module that
had zero coverage before (CLAUDE.md flagged this one by name) --
including the core claim directly: the same 2% price disagreement
flags "mismatch" on a liquid stock but "ok" on an illiquid one at the
same base threshold. Verified against real afx data (SCOM/DTK get the
1x threshold, thinner AMAC gets 3x) and the fallback chain forced end-
to-end (afx failure correctly triggers the PDF path, which itself
degrades to "unverified" cleanly since this sandbox has no tesseract
binary installed -- a real environment limitation, not a code bug;
the OCR dependency chain itself is unit-tested with mocks per CLAUDE.md's
no-live-network rule for tests).


6. FUNDAMENTALS HAVE NO CROSS-CHECK AT ALL
--------------------------------------------------------------
Where: src/fundamental_analysis.py

Current: prices are validated against a second source (price_validation.py);
fundamentals (EPS, revenue, margins, ROE, etc.) come from TradingView's
scanner alone with no independent check.

Problem: one bad/stale TradingView field flows straight into the score
with no sanity check.

Fix: add basic bounds/sanity checks (e.g. reject negative revenue,
implausible ROE, EPS growth that contradicts reported net income
direction). Where feasible, cross-check against the NSE dividend/earnings
calendars already scraped in src/dividend_calendar.py and
src/earnings_calendar.py, following the same verified/corrected/
uncross-checked pattern already used for dividends.


7. NO OUTLIER / BAD-TICK DETECTION ON OHLCV DATA
--------------------------------------------------------------
Where: src/data_acquisition.py, src/analysis_engine.py

Current: no visible filtering of anomalous bars before computing RSI,
MACD, Bollinger Bands, ATR, etc.

Problem: a single bad print (stale duplicate, decimal error, erroneous
spike) can distort indicators for the rest of the lookback window.

Fix: add a lightweight sanity filter on incoming OHLCV bars (e.g. flag/
drop bars where high < low, close outside [low, high], or a single-day
move beyond N standard deviations of recent volatility with no matching
volume spike) before feeding the data into AnalysisEngine.

STATUS (2026-09-04): Done. New utils.filter_ohlcv_outliers(): absolute
sanity (high<low, close/open outside [low,high]) always applies;
statistical outlier detection (>=15 bars needed to judge "normal"
volatility) requires ALL of: the move is >= min_move_pct (15%, see
below), beyond std_threshold (6.0) standard deviations of the stock's
own trailing 20-day volatility (never one flat threshold for every
stock), the price reverts close to its pre-anomaly level the very next
bar (a bad print snaps back; a real repricing persists), and no matching
volume spike (>=3x trailing average -- a huge move on huge volume is a
real event, not a bad print). Wired into data_acquisition.py's
fetch_stock_data() -- the single choke point every source (TradingView/
NSE PDF/Yahoo) passes through -- so cached data is always the filtered
result, applied before AnalysisEngine ever sees the bars.

The min_move_pct floor exists because live testing against real NSE
data caught two false positives the sigma+volume-spike design alone
(the spec's own literal suggestion) did NOT catch: an ordinary ~6.6%
EQTY move and a ~4% ABSA move, both after unusually calm stretches,
registered as 6-8 sigma "anomalies" purely because the recent
volatility baseline was small -- normal price action, not data errors.
Added the reversion check first (didn't fully fix it: a real spike-
then-partial-fade can look similar), then the 15% absolute floor
(real bad prints -- decimal errors, wrong-symbol duplicates -- are
typically far larger than ordinary daily moves regardless of local
volatility). Re-verified clean (0 drops) across the full 57-stock
universe after the fix. 11 tests, including one that directly encodes
the EQTY regression case so it can never silently reappear.


8. NO SHORT-TERM VS LONG-TERM HORIZON CLASSIFICATION
--------------------------------------------------------------
Where: src/scoring.py, src/report_generator.py, templates/

Current: a stock gets one "Buy/Sell/Hold"-style signal and one overall
score, with no indication of the time horizon that signal applies to.

Problem: a technically-driven "bullish" call (RSI bounce, MACD cross) is
actionable over days-to-weeks; a fundamentally-driven "cheap + high
quality + high dividend" call is actionable over months-to-years. Showing
both as the same undifferentiated "Buy" is misleading — a user acting on
a momentum-only signal as if it were a long-term thesis (or vice versa)
can make a bad decision.

Fix: derive a horizon classification per stock from which sub-scores are
actually driving the call:
  - SHORT-TERM (days-weeks): momentum/technical sub-score dominates
    (fresh MACD cross, RSI oversold bounce, near support/resistance).
    Suggested holding period tied to the signal type, e.g. "1-4 weeks"
    for a MACD cross, "days" for an RSI oversold bounce.
  - LONG-TERM (months-years): value/quality/dividend sub-scores dominate
    and agree (cheap vs sector + strong ROE/margins + sustainable yield).
    Suggested holding period e.g. "6-12+ months", tied to typical
    earnings-cycle/dividend-cycle timeframes.
  - MIXED/UNCLEAR: sub-scores conflict (e.g. cheap fundamentally but
    bearish technically) — surface this explicitly rather than forcing
    a single label.
Implementation: add a `horizon` field to score_stock()'s output (label +
suggested time period string + which sub-scores drove the classification,
for transparency — consistent with the "reasons" transparency pattern
already used elsewhere in scoring.py). Display it next to the existing
score/signal on the dashboard and individual stock reports.

STATUS (2026-09-03): Done. score_stock() now always returns a `horizon`
dict ({label, period, drivers, reason}) via new _classify_horizon()/
_short_term_trigger() in scoring.py -- rule-based on which sub-scores
dominate (momentum >=65 alone -> SHORT-TERM, period tied to the specific
trigger: MACD bullish cross "1-4 weeks", golden cross "1-3 months", RSI
oversold "days"; value+quality+dividend all >=65 avg and each >=50 ->
LONG-TERM "6-12+ months"; both strong -> LONG-TERM with a tailwind note;
explicit conflicts, e.g. the spec's own "cheap fundamentally but bearish
technically" example -> MIXED, never forced into one label; no data ->
UNCLEAR). Displayed in all four places the spec asked for: Overview
table's new sortable Horizon column (color-coded badge), the Overview
hover tooltip, the Compare tab (label/period/reason rows), and a new
"Horizon" card on individual stock report pages (also fixed: those
pages' nav bar was missing the Compare tab link, added while in there).
8 new tests (short-term w/ MACD-cross and RSI-oversold triggers,
long-term alone and with tailwind, both MIXED conflict directions,
UNCLEAR, and wiring into score_stock()). Verified against a real
57-stock build + individual stock report + headless-browser screenshots.


PRIORITY ORDER (suggested)
--------------------------------------------------------------
1. Item 1 (sector-relative scoring) — quick win, data already exists.
2. Item 8 (short/long-term horizon) — high user value, builds on existing
   sub-scores, no new data source needed.
3. Item 2 (backtesting) — foundational for calibrating everything else.
4. Item 5 (price validation fallback source + liquidity-scaled threshold).
5. Item 7 (OHLCV outlier detection) — data integrity foundation.
6. Item 6 (fundamentals cross-check).
7. Item 4 (momentum double-counting audit).
8. Item 3 (weight recalibration) — depends on item 2's backtest data.
